v5.0.0-beta1：长期记忆从「检索片段」升级为「可引用、可追溯的结构化知识」——新增知识层与实体图谱，并带来 IM 收件箱、会话归档和可安装的 PWA 界面。

## 🧠 新增：知识层

- 知识页是一等数据：实体 / 项目 / 主题 / 决策 / 速记五类，带标题、正文、状态（生效 / 待审 / 归档）与版本；只有「生效」参与检索、注入和双链解析
- 来源校验是写入闸门：每条引用必须对应数据库里真实存在的记忆、消息或会话，出现一个查不到的 id 就整篇拒绝——页面不能引用没人能核对的证据
- `[[slug]]` / `[[类别/slug]]` 双链在写入时解析成链接，支持反查；指向尚未存在的页面标为「悬空」但仍会保存，引用图允许不完整
- 每个会话有自己的知识：页面按 `channel:<会话>` / `telegram:session:<id>` / 全局 归档，读取规则统一为「本会话 + 全局」——A 群的策展不会改写 B 群同一主题的页面
- 更新是乐观锁：必须带上读到的版本号，否则被拒并回传当前正文供重新合并，不会覆盖别人刚写的内容
- 检索三条道由一个排序器融合：`session_search`（原话）、记忆、知识页按 RRF 排名合并；同一事实既有页面又有记忆时以页面为准
- 每轮注入有硬预算 ≤400 token（近期对话 ≤250 + 可用页标题 ≤150），只给标题，正文一次 `knowledge_get` 取
- 策展三档：`nightly`（每晚补齐、漏掉的夜晚可补）、`manual`（显式触发）、`off`；`curate.shadow: true` 时新页进「待审队列」，在人工批准前对搜索、注入与 agent 全部不可见
- 什么算知识不是配置项：必须有名可指的主体，且达到独立来源数量门槛或由你明确要求——门槛可调，规则本身在代码里

## 🕸️ 新增：实体图谱

- 图谱是记忆的派生视图，不是第二个存储：记忆里被明确断言的关系投影成一条边，删掉来源记忆它也就失去依据
- 「节点是提及，边是陈述」：名字出现在记忆里就够成为节点，但共现不算关系——32 条记忆提到 Ubuntu，图谱会认识 Ubuntu，却不会替你编出关系
- 关系词表覆盖工具与依赖（使用 / 依赖 / 属于 / 扩展，加上人物五项），否则工具类语料只能回答「共现」
- 事实带时间：每条边有生效与失效时间，失效的关系被关闭而非删除，所以「六月时是什么样」仍然可问
- 三道校验：端点必须是文本里真实出现且分词对齐的名字、记忆必须真的断言了这个关系、词序不能是可证的反向（被动句除外）；无法证实的一律不写
- 图谱自愈：每次同步关闭被矛盾的关系、删除没有任何记忆证实的开放边、合并同名节点；别名只从语料里的明确说法提取（括号、又称 / 简称 / aka），不靠模型猜——错合并不可恢复
- 边权重可在读取时按时间衰减（默认关闭）
- 读取面：`entity_query` 工具 + `/api/graph` + WebUI「图谱」页（搜索、按种类筛选、抽屉展开、一键诊断「有关联」与「仅共现」）；`graph:export` 可导出 Obsidian 风格 vault

## 📥 新增：收件箱与归档

- 收件箱只读展示飞书 / Telegram / 微信 / QQ 的会话原文，支持重命名与删除、分页浏览；不提供回复，避免重复投递与消息回环
- 机器人名字从平台自己读取（飞书 bot info、Telegram getMe、QQ users/@me），缓存一天并落盘，离线重启也仍显示正确的群名
- `/new` 开启真实的新会话，`/new <标题>` 直接命名
- 自动归档：超过 N 天未活动的会话移入「归档」，项目会话与 IM 收件箱都支持，批量归档 / 删除，也可立即清空积压；只影响列表，记忆与搜索不受影响
- 手工恢复的会话不会被下一次归档扫描再吞掉；维护任务每 2 小时扫一次，运行记录保留 90 天

## 🖥️ 界面

- WebUI 新增「知识库」页：知识页 / 待审队列 / 图谱三个页签；待审卡片展示证据而非置信度，可批准或带理由驳回
- 设置页新增「知识与检索」分组：整层开关、页面统计、策展与注入开关（关闭时明确说明「不写入、不注入、不参与检索，已有页面仍在库里」）
- 可安装为 PWA（manifest / service worker / 图标），修复 iOS 聚焦缩放、输入框满宽与安全区

## 🚦 状态与开关

- **知识层默认关闭**：`config.yaml` 缺少 `knowledge:` 整节即为关闭，`knowledge: {}` 才是打开——新子系统不会在升级时自己打开；关掉后已有页面与来源仍保存在库里
- 图谱默认开启，但只做投影、维护与只读查询，不改变对话行为
- 策展默认 `nightly`；要人工把关请设 `knowledge.curate.shadow: true`
- 写入类工具（`knowledge_write`）保留审批；查询类工具（`session_search`、`knowledge_search`、`knowledge_get`、`entity_query`）为只读
- 知识页保存在 `app.db` 内，备份请针对数据库与导出目录，而不是 vault

v5.0.0-beta1 turns long-term memory from "retrieved fragments" into structured knowledge you can cite and trace: a new knowledge layer and entity graph, plus an IM inbox, conversation archiving and an installable PWA.

## 🧠 New: Knowledge Layer

- Knowledge pages are first-class rows: entity / project / topic / decision / snippet, each with a title, body, status (active / pending / archived) and version; only `active` pages take part in retrieval, injection and link resolution
- Source verification gates every write: each citation must resolve to a real memory, message or session in the database — one unknown id refuses the whole page, so nothing can cite evidence nobody can check
- `[[slug]]` / `[[type/slug]]` wikilinks are parsed at write time and can be read backwards; a link to a page that does not exist yet is reported as *dangling* but still saved, because a citation graph is allowed to be incomplete
- Every conversation has its own knowledge: pages are scoped to `channel:<chat>` / `telegram:session:<id>` / global, and every read applies the same rule — this conversation plus global — so curating in one chat cannot rewrite another chat's page on the same subject
- Updates are optimistic: an update must carry the version it read or it is refused and handed the current body to re-merge, so it cannot clobber what someone else just wrote
- Three retrieval lanes are fused by one ranker: `session_search` (what was said), memories, and knowledge pages interleave by RRF rank; where a page and a memory state the same thing, the page wins
- Per-turn injection has a hard budget of ≤400 tokens (recent conversation ≤250 + available page titles ≤150) — titles only, with the body one `knowledge_get` away
- Curation has three modes: `nightly` (catch-up capable — a night the device slept through is not a lost night), `manual`, and `off`; with `curate.shadow: true` new pages land in a review queue and stay invisible to search, injection and the agent until approved
- What counts as knowledge is code, not config: a nameable subject plus enough independent sources, or an explicit request — the thresholds are knobs, the rule itself is not

## 🕸️ New: Entity Graph

- The graph is a derived view of memory, not a second store: a relation a memory actually asserts becomes an edge, and deleting the source memory takes its evidence with it
- A node is a mention, an edge is a statement: naming something in a memory is enough to become a node, but co-occurrence is never a relation — 32 memories may mention Ubuntu without the graph inventing what it is connected to
- The relation vocabulary covers tools and dependencies (USES / DEPENDS_ON / PART_OF / EXTENDS alongside the social five); without it a tool corpus could only ever answer "mentioned"
- Facts carry time: every edge has a validity window, a fact that stops being true is *closed* rather than deleted, so "what was true in June" stays answerable
- Three gates before anything is written: both endpoints must appear in the text and be token-aligned, the text must really assert the relation, and the word order must not be a provable reversal (passives excepted); whatever cannot be verified is not written
- The graph self-heals on every sync: contradicted relations are closed, open edges no memory attests are deleted, and nodes duplicated across spellings merge; aliases come only from explicit definitions in the corpus (brackets, 又称 / 简称 / aka), never from a model's guess, because a wrong merge is unrecoverable
- Edge weight can decay over time at read time (off by default)
- Read surfaces: the `entity_query` tool, `/api/graph`, and the WebUI Graph tab (search, kind filter, drawer drill-down, one-click diagnosis separating "connected" from "co-mentioned"); `graph:export` writes an Obsidian-style vault

## 📥 New: Inbox and Archive

- The inbox shows Feishu / Telegram / WeChat / QQ transcripts read-only, with rename, delete and paging; there is no reply path, so duplicate delivery and message loops stay impossible
- Bot names are read from the platforms themselves (Feishu bot info, Telegram getMe, QQ users/@me), cached for a day and persisted, so a restart — even offline — still labels each group correctly
- `/new` opens a real conversation, and `/new <title>` names it
- Auto-archive moves conversations idle for N days into Archive, for project chats and the IM inbox alike, with batch archive / delete and a button that drains the whole backlog; only the list is affected — memory and search are not
- A conversation you restore by hand survives the next sweep; the maintenance job runs every two hours and keeps 90 days of run history

## 🖥️ Interface

- New Knowledge page in the WebUI with three tabs — pages, review queue, graph; review cards show evidence rather than confidence, and a draft can be approved or rejected with a reason
- New "Knowledge & Retrieval" settings group: the master switch, page counts, curation and injection toggles — with the off state spelling out that nothing is written, injected or searched while existing pages stay in the database
- Installable as a PWA (manifest, service worker, icons), plus fixes for iOS focus zoom, full-width composer input and safe areas

## 🚦 State and Switches

- **The knowledge layer is off by default**: a `config.yaml` without the `knowledge:` section means disabled, and `knowledge: {}` is the opt-in — a new subsystem must not switch itself on during an upgrade; turning it off keeps existing pages and sources in the database
- The graph is on by default, but only projects, maintains and answers read-only queries — it never changes conversation behavior
- Curation defaults to `nightly`; set `knowledge.curate.shadow: true` to gate new pages through human review
- Writes (`knowledge_write`) still require approval; queries (`session_search`, `knowledge_search`, `knowledge_get`, `entity_query`) are read-only
- Knowledge pages live inside `app.db`, so back up the database and the export directory rather than a vault
